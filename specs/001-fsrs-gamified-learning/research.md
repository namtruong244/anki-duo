# Research: FSRS Gamified Learning App (MVP)

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-11-05

Each entry records the decision, why it was chosen, and what else was considered.

**Revision 2026-11-05 (b)**: the project owner set two deployment goals:
1. run on cloud free tiers (AWS Lambda);
2. add a **Flutter** mobile app later.

Because of this, the single Next.js app (revision a) was replaced with:
- a static Vite + React PWA;
- a Hono API on AWS Lambda;
- a pnpm monorepo.

R1, R3, R4, R8, R10 and R16 were rewritten, and R17–R18 were added.

**Revision 2026-11-05 (c)**: S3 has no always-free tier, so hosting the web there would not cost
exactly $0. The web is now served by Cloudflare Workers Static Assets, and a small Worker proxies
`/api/*` to the Lambda. CloudFront and S3 are no longer used. Only R16 changed.

## R1. Application architecture and runtime

- **Decision**: a pnpm-workspaces monorepo, all TypeScript `strict`.
  - **`apps/web`**: Vite + React 19 single-page PWA, built to static files.
  - **`apps/api`**: a Hono HTTP API. The same app object runs on AWS Lambda in production
    (`hono/aws-lambda`) and on Node.js 24 locally (`@hono/node-server`).
  - **`packages/domain`**: pure TypeScript rules (scheduler, queue, path, XP, streak, study day,
    stats). Imported by web and API.
  - **`packages/contract`**: Zod schemas for every request and response. The OpenAPI document is
    generated from them with `@hono/zod-openapi`.
  - **`packages/fixtures`**: language-neutral JSON golden test cases (see R17).

  Routing in the SPA uses React Router (library mode). Online-only API calls use `openapi-fetch`,
  typed from the OpenAPI document.
- **Rationale**:
  - A static SPA can be hosted almost free and can be wrapped later if needed.
  - Hono is a small, standards-based (Fetch API) framework that runs unchanged on Lambda,
    Cloudflare Workers, Node or Bun, so the hosting choice stays reversible.
  - The app sits behind sign-in, so server-side rendering and SEO add little; a static landing
    page covers marketing.
  - Splitting web and API produces the clean, versioned HTTP API a Flutter client needs.
- **Alternatives considered**:
  - Next.js via OpenNext on Lambda or Cloudflare was rejected because of its larger cold-start
    bundles and an adapter layer to maintain, and its server components don't help an offline
    SPA.
  - Fastify or Express on Lambda was rejected: they aren't Fetch-native, so they're harder to move
    to Workers later.
  - TanStack Router was rejected as unnecessary for about 12 screens.

## R2. FSRS implementation

- **Decision**: Use `ts-fsrs`, the reference TypeScript implementation maintained by the
  open-spaced-repetition organisation, pinned to an exact version. Use its default FSRS
  parameters, the target retention set by the learner (FR-004), and its learning steps. Wrap it in
  a project module `packages/domain/src/scheduler/` that:
  - takes the review time, card state, grade and parameters as arguments (no `Date.now()`, no
    randomness unless a seed is passed in);
  - turns interval fuzz off, or seeds it from the card id plus review count, so replays are exact;
  - stamps every review log with the algorithm and library version used.
- **Rationale**: Constitution Principle I requires a published algorithm and a pure, deterministic
  scheduler. `ts-fsrs` follows the reference implementation and ships its own test vectors, which
  we import as fixtures (SC-004). Running the same module in the browser (optimistic update, FR-016)
  and on the server (replay, FR-030a) gives identical results by construction.
- **Alternatives considered**: Writing FSRS from scratch was rejected because of the bug risk
  (Principle II) and the cost of tracking upstream parameter changes. Calling the Python/Rust FSRS
  implementations was rejected: they can't run in the browser offline.

## R3. Database and ORM

- **Decision**: PostgreSQL (Neon, region `aws-ap-southeast-1`, the same region as the Lambda),
  accessed through Drizzle ORM with Neon's serverless driver (HTTP/WebSocket). Lambda therefore
  needs no connection pool. Migrations are generated by `drizzle-kit` and committed to
  `apps/api/drizzle/`. Integration tests run against PGlite (Postgres compiled to WASM,
  in-process) through the same Drizzle schema.
- **Free-tier note**: Neon's free plan offers about 0.5 GB per project; check current limits.
  ReviewLog is the table that grows. To stretch the free tier, `state_before` and `state_after`
  are stored as compact `double precision[8]` arrays instead of JSON objects. This roughly
  halves the row size (estimated ~300 B per row including indexes), which fits about 1.5 million
  reviews: 1,000 active learners × 50 reviews/day for about a month. This is enough for the MVP
  launch. Real usage beyond that means moving to Neon's paid plan, which needs no code change.
  Free-plan storage is checked in the load test (V12).
- **Rationale**: The data is relational (learner → deck → card → review log). The heatmap and
  dashboard need aggregate queries. Drizzle is typed SQL with a thin runtime and no code-generation
  step. PGlite gives real Postgres semantics in tests without Docker, keeping tests fast and
  deterministic.
- **Alternatives considered**: Prisma was rejected because of its heavier runtime and engine
  binaries on serverless. SQLite/Turso was rejected because Neon's serverless Postgres has a free
  tier that fits the scale (≤1,000 learners), and PGlite covers fast local tests.

## R4. Authentication

- **Decision**: Better Auth with its Drizzle adapter. It provides:
  - email + password, with required email verification and password reset;
  - Google OAuth;
  - database-backed sessions in an httpOnly, secure cookie;
  - built-in rate limiting on auth routes;
  - an account-deletion hook.
  Transactional email (verification and reset) is sent through Resend.
- **Clients**:
  - **Web**: the SPA and API share one origin through the Cloudflare Worker (R16), so the web
    uses Better Auth's httpOnly
    `SameSite=Lax` cookie, which avoids CORS and third-party-cookie problems.
  - **Flutter (later)**: Better Auth's `bearer` plugin issues the same session as an
    `Authorization: Bearer` token, kept in secure storage. Google sign-in on mobile sends the
    native Google ID token to Better Auth's social sign-in with `idToken`.
  - Both auth schemes are declared in [contracts/openapi.yaml](./contracts/openapi.yaml).
- **Rationale**: Spec Assumptions need email/password with verification and reset plus Google
  sign-in. Auth.js supports email/password only through its Credentials provider, which leaves
  verification, reset, hashing and rate limiting to custom code. Better Auth provides all of these,
  stores sessions in our Postgres, and mounts as a Hono handler (`/api/auth/*`). Password hashing
  (scrypt) needs more CPU than the Cloudflare Workers free tier allows per request, but it is fine
  on Lambda. This was one reason to pick Lambda.
- **Alternatives considered**: Auth.js was rejected for the reasons above. Clerk and Supabase Auth
  were rejected: they're external identity silos and add vendor coupling. Amazon Cognito was
  rejected: its hosted UI and SDK are heavy for a small app, and it would split user data from
  Postgres.

## R5. Media storage

- **Decision**: Cloudflare R2 (S3-compatible), private bucket. Uploads use short-lived presigned
  PUT URLs issued by `/api/v1/media/upload-url`. The client uploads directly to R2 and then
  confirms the upload. Reads go through `/api/v1/media/{id}`, which checks ownership and redirects
  to a presigned GET URL; the service worker caches the bytes. Size limits (5 MB per file, 500 MB
  per learner) and MIME allow-lists are enforced when issuing the URL and again when confirming.
  The R2 bucket has a CORS rule that allows `GET`/`PUT` from the app origin, so the service
  worker can cache media responses.
- **Rationale**: R2 has no egress fees (free tier about 10 GB stored), which matters because media
  is downloaded again on every device for offline use. Direct upload keeps large bodies away from
  Lambda (6 MB request payload limit). Checking ownership on read keeps media private per account.
  Presigned URLs work the same for a Flutter client.
- **Alternatives considered**: Storing media in Postgres (`bytea`) was rejected because it bloats
  backups and slows queries. Vercel Blob was rejected because egress costs grow with offline
  prefetching. AWS S3 was rejected because egress is billed.

## R6. Offline-first client store and sync

- **Decision**:
  - **Local store**: IndexedDB through Dexie holds the learner's decks, cards (content and current
    FSRS state), settings, daily activity, and an outbox of pending review events. All reads in a
    session come from IndexedDB, never the network.
  - **Writes during review**: grading runs the scheduler locally, then in one Dexie transaction
    updates the card and appends a `ReviewEvent` with a client-generated UUIDv7 id to the outbox.
    The UI moves to the next card before the transaction resolves (optimistic update, FR-016).
  - **Push**: `POST /api/v1/sync/push` sends outbox events in batches of up to 500. The server
    inserts them idempotently (`ON CONFLICT (id) DO NOTHING`), so a retry never double-applies.
  - **Replay on the server**: if an event's `reviewedAt` is older than the card's last review
    (the conflict case), or if an undo is applied, the server rebuilds the card's FSRS state by
    replaying all non-revoked review logs in `(reviewed_at, id)` order through the same scheduler.
  - **Pull**: `GET /api/v1/sync/pull?cursor=` returns everything changed since a monotonically
    increasing server change sequence (a Postgres `bigserial`). Rows changed on the server always
    overwrite the local copy, except cards with unsent outbox events; those are re-derived after
    the push.
  - **When sync runs**: on app start, when connectivity returns (`online` event), every 30 s while
    the app is visible and online, and after each session. This meets the ≤1 minute cross-device
    target (FR-030a, SC-008).
  - **Online-only edits**: deck/card create, edit, delete and import (clarification Q2) call REST
    endpoints directly. Their results are written to Dexie, and the UI disables them while offline.
- **Storage boundary**: the sync engine and session logic in `apps/web` talk to a `LocalStore`
  interface, not to Dexie directly. Dexie is the web implementation. The Flutter app will
  implement the same contract on SQLite (drift), and the protocol itself is plain HTTP + JSON.
- **Rationale**: Reviews are append-only facts, so syncing them needs no merge logic, only
  idempotent insert plus deterministic replay. This keeps Principle I's "review history persisted
  losslessly" true even with concurrent devices. Making content edits online-only removes the hard
  conflict cases. The local store keeps only current card state, not full review history, which
  keeps IndexedDB small at 20,000 cards (SC-010).
- **Alternatives considered**: CRDT/sync engines (Replicache, ElectricSQL, PowerSync, RxDB) were
  rejected: they add a dependency and a server component well beyond what an append-only event
  stream needs. Last-write-wins on card state was rejected because it loses reviews, which the
  constitution forbids.

## R7. Undo

- **Decision**: Undo marks the latest review as revoked rather than deleting it.
  - If the event is still in the outbox, the client drops it and restores the previous card
    snapshot it kept in memory.
  - If the event has already been pushed, the client sends a `revoke` event that references the
    review id. The server sets `revoked_at`, replays the card's history, and reverses the XP.
- **Rationale**: History stays append-only and auditable. Replay is the same mechanism used for
  conflicts, so there is only one code path to test.
- **Alternatives considered**: Hard-deleting the review row was rejected because it breaks
  idempotency (a re-pushed event would come back) and loses audit history.

## R8. PWA shell and service worker

- **Decision**: Use `vite-plugin-pwa` in `injectManifest` mode with a custom `src/sw.ts` built on
  Workbox modules.
  - The app shell and hashed static assets are precached.
  - SPA navigations fall back to `index.html`.
  - API GETs use network-first, falling back to cache.
  - `/api/v1/media/*` uses cache-first in a dedicated media cache.
  - After each pull, the client asks the service worker to prefetch media for today's due and new
    cards and to evict media no longer referenced by today's queue, beyond a 200 MB cache budget.
  - The web app manifest is generated by the plugin.
- **Rationale**: Meets "installable" (constitution) and offline review with media (clarification
  Q2, FR-017). This is the standard, well-maintained PWA tooling for Vite. `injectManifest` keeps
  full control over the media cache logic.
- **Alternatives considered**: A hand-written service worker was rejected because cache versioning
  and precache manifests are error-prone. `@serwist/vite` is equivalent, but its Vite integration
  is less widely used.

## R9. Styling, motion and sound

- **Decision**:
  - **Styling**: Tailwind CSS v4 with design tokens (colours, radii, the 3D "chunky" button bottom
    border and press offset) as CSS variables in `src/styles/tokens.css`.
  - **Motion**: Motion (formerly Framer Motion) for the progress bar spring, card transitions and
    node unlocks. All motion goes through a `useReducedMotion` wrapper that falls back to fades
    (FR-022).
  - **Sound**: a small Web Audio wrapper that preloads short OGG/MP3 sprites, plays only after the
    first user gesture, and respects the sound setting (FR-021).
  - **Charts**: the heatmap and donut ring are hand-built SVG components.
- **Rationale**: Tailwind tokens make the Duolingo-like visual language consistent and themeable.
  Motion handles spring physics and layout animations with little code. Two simple charts don't
  justify a charting library, and custom SVG gives full control over accessible labels (FR-028).
- **Alternatives considered**: CSS-only animation was rejected because spring-based progress bars
  and orchestrated celebrations are hard to do well. Howler.js was rejected: Web Audio covers the
  need without a dependency. Recharts and nivo were rejected as heavy for two charts.

## R10. Internationalisation

- **Decision**: i18next + react-i18next with ICU message format (`i18next-icu`). Catalogs are
  `apps/web/src/i18n/messages/{vi,en}.json`.
  - The initial locale comes from `navigator.languages` (`vi*` → Vietnamese, anything else →
    English).
  - The chosen locale is saved to the learner's settings and then wins over the browser.
  - No locale prefix in URLs: it's an app behind sign-in.
  - A test fails the build if any key is missing from either catalog (SC-009).
  - API error messages are not translated: the API returns stable `code`s and clients translate
    them.
- **Rationale**: The most widely used client-side i18n stack, with ICU plurals. Flat ICU JSON
  converts mechanically to Flutter's ARB format, so the mobile app can reuse the same
  translations.
- **Alternatives considered**: next-intl was dropped along with Next.js. Lingui was rejected
  because its compile step adds build complexity. Paraglide was rejected because it is less
  established.

## R11. Markdown rendering and safety

- **Decision**: `react-markdown` + `remark-gfm` (tables, lists) + `rehype-sanitize` with a strict
  schema: no raw HTML, `javascript:` URLs stripped, external images allowed only over `https`.
  Inline SVG uploads are served with `Content-Type: image/svg+xml` and shown only through `<img>`,
  which never executes scripts.
- **Rationale**: FR-010 and FR-034, and the Markdown/HTML edge case. React escapes text by default,
  and sanitisation covers what the Markdown AST allows.
- **Alternatives considered**: `marked` + DOMPurify was rejected: it outputs HTML strings that need
  `dangerouslySetInnerHTML`. MDX was rejected because it executes code and is unsafe for
  user-supplied content.

## R12. CSV/TSV import

- **Decision**:
  - Parse on the client with Papa Parse inside a Web Worker. It auto-detects the delimiter; header
    detection is a heuristic (first row is non-empty and distinct, matching known names like
    front/back/tags/mặt trước/mặt sau).
  - The learner maps columns and sees a preview.
  - Validated rows go to `POST /api/v1/decks/{deckId}/import` in chunks of 1,000 rows with an
    `importJobId` and duplicate mode. The server dedupes on the normalised Front text within the
    deck and returns per-row results.
  - Limits: 10,000 rows, 10 MB, UTF-8 (UTF-8 BOM accepted; other encodings rejected).
- **Rationale**: Parsing locally gives an instant preview and keeps requests under the
  serverless body limit. Ten chunks of 1,000 rows fit comfortably in the 15 s target (SC-006).
- **Alternatives considered**: Uploading the file and parsing it on the server was rejected: it
  hits the body-size limit and delays the preview.

## R13. Export format

- **Decision**: `anki-duo-export` JSON format, version 1, documented in
  [contracts/export-format.md](./contracts/export-format.md). It contains the deck, its cards
  (content and FSRS state), the full review history (including revocations) and media manifest
  entries with download URLs. A media ZIP is optional. Re-import replays history, so the
  scheduling state is identical (FR-014).
- **Rationale**: Open, documented and human-readable, as the constitution requires. Exporting the
  history (not just the state) means a future algorithm change can recompute schedules.
- **Alternatives considered**: Anki `.apkg` was rejected: importing it is out of scope, and
  writing a correct SQLite-based package is a sizeable feature of its own. CSV-only export was
  rejected because it can't carry review history cleanly.

## R14. Day boundary, XP and streak computation

- **Decision**:
  - A learner's "study day" is computed by a pure function from an instant, the learner's IANA
    time zone (auto-detected and saved in settings), and the day-start hour (default 04:00).
  - XP per review is a pure function of whether the card was due or new: 2 XP whatever the
    grade, 0 for study ahead. The grade never changes XP, so honest grading is never penalised
    (constitution Principle I). Each finished session adds a 5 XP bonus (FR-024).
  - `DailyActivity` rows are derived on the server from review logs and session completions.
    Rows are recomputed for the affected days on push and on revoke.
  - The streak is derived from DailyActivity, where `goalMet = xp ≥ goal OR allAvailableDone`.
  - The client computes the same values optimistically with the same domain functions.
- **Rationale**: Deriving everything from review logs means XP and streaks can never disagree
  with history. Keeping these functions in `packages/domain` (no I/O) keeps them testable with
  injected time (Principle II) and separate from the scheduler (Principle I, FR-007).
- **Alternatives considered**: Storing XP as a mutable counter was rejected because it drifts on
  undo or conflict.

## R15. Testing strategy

- **Decision**:
  - **Vitest** for unit tests (domain, scheduler and FSRS vectors, XP/streak, path, import
    parsing) and integration tests (Hono API handlers against PGlite; Dexie against
    `fake-indexeddb`).
  - **Playwright** for end-to-end tests: mobile (Pixel 7 profile, 320 px) and desktop (1440 px)
    projects, offline scenarios via `context.setOffline`, two-device sync with two browser
    contexts, and accessibility checks with `@axe-core/playwright`.
  - All tests inject a fixed clock (`vi.useFakeTimers` / clock argument). Tests have no network
    access except Playwright hitting the local app.
- **Rationale**: Constitution Principle II (deterministic, test-first). Covers SC-001, SC-005,
  SC-007, SC-008 and WCAG AA.
- **Alternatives considered**: Jest was rejected because it is slower and has weaker ESM/TS
  support. Cypress was rejected: it supports multiple browser contexts (two devices) poorly.

## R16. Hosting, CI and observability

- **Decision**: the user-facing edge is on Cloudflare; the API runs on AWS Lambda in
  `ap-southeast-1` (Singapore, close to Vietnamese users). Both are defined as code in one
  `sst.config.ts` (SST v3 with the AWS and Cloudflare providers).
  - **One Cloudflare Worker with Static Assets** (`apps/edge`), giving the browser one origin:
    - **Static files**: `apps/web/dist` is uploaded as the Worker's static assets, with SPA
      fallback to `index.html`. Asset requests are served by Cloudflare without running the
      Worker script. A `_headers` file sets long-lived caching for hashed assets and
      `no-cache` for `index.html` and `sw.js`.
    - **API proxy**: the Worker script runs only for `/api/*` and forwards the request to the
      Lambda Function URL. It keeps the method, path, query, body (streamed) and headers,
      including `Cookie`. It strips any incoming `x-origin-secret`, adds its own
      `x-origin-secret`, and sets `x-forwarded-for` (from `CF-Connecting-IP`) and
      `x-forwarded-host`. The response, including `Set-Cookie`, goes back unchanged and
      uncached.
    - Because the browser sees one origin, the session cookie is first-party and no CORS is
      needed. The free `*.workers.dev` subdomain works, so a custom domain is optional (it can be
      added later on Cloudflare).
  - **Lambda Function URL protection**:
    - the Function URL is public (auth type NONE), but a Hono middleware rejects with 403 any
      request whose `x-origin-secret` doesn't match, using a constant-time compare;
    - the secret is an SST secret, set on both the Worker and the Lambda, and can be rotated
      without downtime by accepting two values during rotation;
    - Better Auth's `baseURL` and trusted origin are the Worker's URL.
  - **Lambda**:
    - runtime: the newest Node.js LTS that Lambda supports;
    - `arm64`, 512 MB, 15 s timeout;
    - one function for the whole Hono app, bundled with esbuild and kept small for cold starts.
    Cold starts only affect sync and online edits; grading never waits for the network.
  - **Secrets** (database URL, auth secret, origin secret, R2 keys, Resend key, Google OAuth)
    are kept as SST secrets, encrypted in SST's state and injected into the Lambda and Worker.
  - **Other services**: Neon (R3), R2 (R5, on the same Cloudflare account as the Worker),
    Resend (R4).
  - **Free-tier fit** (check current limits before launch):
    - Cloudflare static assets: unlimited requests and bandwidth on the free plan.
    - Cloudflare Worker script: 100k requests/day and 10 ms CPU each. Only `/api/*` calls count:
      about 10k/day at the spec's scale (100 users syncing every 30 s while active). The proxy
      only forwards bytes, and time spent waiting on Lambda is not CPU time.
    - Lambda: 1M requests and 400k GB-s per month, always free; about 300k requests per month
      expected.
    - R2: 10 GB storage free, no egress fees.
    - Resend: about 3,000 emails per month.
    - Neon: about 0.5 GB, the first limit to bind (R3).
    - CloudWatch Logs: 5 GB per month.
  - **Cost guard**: SST creates an AWS Budgets alert at $1/month. Cloudflare's free plan has no
    paid overage: exceeding the Worker limit returns errors instead of charges, and the client
    treats those as offline and retries.
  - **Environments**: `dev` (each developer's own stage), `staging` and `prod` stages via
    `sst deploy --stage`.
  - **Pre-merge check**: `pnpm verify` runs typecheck, lint, unit, integration, contract and
    fixture tests, and the full Playwright suite (all specs, `mobile` and `desktop` projects). k6
    load tests are a release check, not part of the test suite. It runs locally and, once the repo is on
    GitHub, in a GitHub Actions workflow that can also run `sst deploy --stage staging`.
  - **Observability**:
    - API handlers log structured JSON (request id, user id hash, route, duration, outcome) to
      CloudWatch Logs, with 14-day retention to stay within the free 5 GB;
    - the client reports sync failures and uncaught errors to `POST /api/v1/client-events`, which
      logs them the same way;
    - the Worker logs only failures to reach Lambda (Workers Logs, free tier);
    - no third-party APM in the MVP.
- **Rationale**: Lowest operating cost for a solo project that still meets the spec's scale. This
  settles the "observability" and "rate limiting" items left open by `/speckit-clarify`:
  - Better Auth rate-limits auth routes;
  - sync and import endpoints enforce batch-size limits and a per-user limit of 60 requests per
    minute, stored in Postgres.
- **Alternatives considered**:
  - CloudFront + S3 for the web (revision b) was rejected: S3 has no always-free tier, so the
    bill is small but not zero.
  - Serving the web from the Lambda behind CloudFront was rejected: a cold start on every cache
    miss, and the cache is empty after every deploy.
  - Cloudflare Pages with a cross-origin Lambda URL was rejected: the session cookie would be
    cross-site, and every API call would need CORS preflights. The Worker proxy keeps one origin.
  - Running the whole API on Cloudflare Workers was rejected for now: password hashing exceeds
    the free CPU limit (R4). Hono keeps it as a later option.
  - API Gateway was rejected: a Function URL is free and simpler.
  - Wrangler-only for Cloudflare plus CDK/SAM for AWS was rejected: two IaC tools and two sets of
    secrets. SST manages both providers in one file, and its state stays in our own account.
  - Self-hosting on a VPS was rejected: it adds ops work.
  - Sentry was deferred until there is real traffic.

## R17. Flutter readiness (mobile app later)

- **Decision**: the web MVP is built so that a Flutter app can join later without changing the
  server or the data.
  1. **OpenAPI is the contract.**
     - `packages/contract` generates the OpenAPI document.
     - A contract test fails if it drifts from [contracts/openapi.yaml](./contracts/openapi.yaml).
     - Flutter will generate its Dart client from that file (e.g. `openapi-generator` dart-dio).
  2. **Server-authoritative scheduling.**
     - Clients compute scheduling optimistically for instant feedback, but the server's replay
       with `ts-fsrs` is the final word, and a pull corrects any difference.
     - Flutter will use the Dart FSRS port (`fsrs` on pub.dev, same organisation).
     - Each review log records `scheduler_version`, so differences can be traced.
  3. **Language-neutral golden fixtures.**
     - `packages/fixtures/*.json` holds input/expected-output cases for every domain rule:
       FSRS vectors, queue building, path assignment and status, XP, streak, study-day
       boundaries and donut classification.
     - Today the TypeScript tests read them. The Dart implementation must pass the same files
       before release.
     - Any rule change starts by editing a fixture, which is a failing test first (Principle II).
  4. **Bearer auth and presigned media** (R4, R5) work unchanged from mobile.
  5. **The `LocalStore` interface** (R6) documents what an offline client must store. Flutter
     implements it with drift (SQLite) and keeps media in its own file cache.
  6. **Translations** are ICU JSON, convertible to ARB (R10).
- **Rationale**: Dart can't import TypeScript, so reuse moves from shared code to shared contracts
  and shared test data. Making the server authoritative means two client implementations can never
  corrupt history (Principle I). In the worst case, a mobile device shows a slightly different
  interval until its next pull.
- **Alternatives considered**:
  - Running the TS domain inside Flutter through a JS engine was rejected because it is complex
    and slow to start.
  - Computing scheduling only on the server was rejected because it breaks offline review.
  - Capacitor or React Native were not chosen, because the owner wants Flutter.

## R18. Local development

- **Decision**:
  - `pnpm dev` starts the Hono API on Node (`:8787`) and Vite (`:5173`). Vite proxies `/api` to
    the API, so local development is same-origin, like production.
  - Local Postgres comes from a Neon dev branch or a local Postgres 16+.
  - Media uses MinIO (S3-compatible) through `docker compose`, or a dev R2 bucket.
  - `sst dev` is optional, for testing against real AWS.
- **Rationale**: Fast feedback without deploying. Same-origin locally avoids cookie and CORS
  differences between development and production.
- **Alternatives considered**: Making `sst dev` the default loop was rejected: it needs an AWS
  account for every change.

## R19. Note types and HTML card rendering

- **Decision**:
  - Note-type fields are edited with **TipTap** (ProseMirror-based) as a WYSIWYG editor, with a
    raw-HTML toggle for advanced edits. Field values are stored as sanitized HTML.
  - Note-type HTML and CSS are sanitized by a **whitelist sanitizer built on `htmlparser2`**. The same
    module runs on the API (on save) and in the web client (on render), so both apply one rule set.
    Scripts, event-handler attributes and unlisted URL schemes are removed. Allowed image sources are
    `https:` or `media:<uuid>`, and allowed link schemes are `http:`, `https:` and `mailto:`. CSS
    `url()`, `expression()`, `@import` and `behavior` are filtered out.
  - Each note-type card renders in a **Shadow DOM** inside the app, so its CSS is scoped to that card
    and the app's design tokens still inherit into it.
  - Legacy cards stay Markdown (R11) and keep the existing Markdown editor and renderer.
- **Rationale**: Anki-style templates need author-controlled HTML and CSS, which the Markdown
  pipeline (R11) cannot express. JavaScript is never allowed, so a sanitized static fragment in a
  Shadow DOM gives the layout freedom without running author code. One sanitizer shared by server
  and client keeps stored and rendered output consistent. TipTap has a mature, extensible
  editor with a clean JSON/HTML output, and it runs in the browser without a server round trip.
- **Alternatives considered**:
  - An `<iframe sandbox>` that allows scripts was rejected. Script execution is out of scope for
    the product, and iframes need postMessage-based height sync and do not inherit app tokens.
  - DOMPurify was rejected for server-side sanitizing because it needs a DOM, which the Node API
    does not have (it would need jsdom). It remains an option for client-only rendering, but it
    would then be a second rule set next to the server's.
  - Keeping only Markdown was rejected because it cannot express the layouts and CSS that note
    types require (FR-010, FR-034).
